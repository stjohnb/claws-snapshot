# dynamic-workflow-runner-scanner

**Source**: `src/jobs/dynamic-workflow-runner-scanner.ts`
**Trigger**: Via `scanner-dispatcher` (daily schedule)

Detects **dynamic workflows** — GitHub-generated jobs with no workflow file in
the tree, such as Dependabot's updater (`dynamic/dependabot/dependabot-updates`)
or CodeQL default setup — executing on billed GitHub-hosted runners instead of
self-hosted ones. Creates a deduped `Priority` alert issue in the offending repo.

## Why this scanner exists separately from `ubuntu-latest-scanner`

`ubuntu-latest-scanner` enforces the same self-hosted-only policy but is
**file-based**: it reads `.github/workflows/*.yml` and regex-matches `runs-on:`.
Dynamic workflows are generated by GitHub from a repository/org *setting*, not
from a file in the tree, so there is no `runs-on:` line anywhere for that
scanner to find — three repos (`home-assistant-config`, `dot-files`,
`vr-rooms`) ran Dependabot's updater on billed `ubuntu-latest` runners
undetected for this structural reason before this scanner was added (#2322).

## Detection

- Fetches the repo's dynamic workflow runs via `gh.listDynamicWorkflowRuns()`
  and narrows them to the runs actually worth checking (`selectScannableRuns()`):
  drops any path under `dynamic/pages/`, keeps only the **latest run per
  remaining distinct path** (`latestRunByPath()`), then drops paths whose
  latest run is older than **14 days**.
- Both exclusions exist because a violation on them can never be remediated
  the normal way. A path whose latest run is 14+ days old has simply stopped
  producing runs — it isn't "running on GitHub-hosted runners" in any
  actionable sense, and without this cutoff its last hosted run would keep
  the alert open forever even after the path went dead (#2339). The legacy
  Pages build (`dynamic/pages/pages-build-deployment`) always executes on
  GitHub's own infrastructure; unlike Dependabot's updater there is no
  runner-label setting that moves it anywhere else, so even a live run there
  produces a permanently unactionable alert — the only real remedy is a
  repo-settings decision (switch the Pages source to GitHub Actions, or
  disable Pages), not a runner change. The 14-day figure is sized against the
  org-standard `interval: weekly` Dependabot schedule (2x the slowest live
  cadence).
- For each remaining latest run, fetches per-job runner identity via
  `gh.getRunJobRunnerInfo()`. This call throws on anything but a deleted run
  (404), so an inconclusive fetch propagates to `run()`'s error handler
  instead of silently reading as "no violations" and closing a live alert.
- A job is flagged (`isGitHubHostedJob()`) when its `runnerGroupName` is
  literally `"GitHub Actions"`, or any of its labels match `^(ubuntu-|windows-|macos-)`.
- Issue title: `Alert: dynamic workflows are running on GitHub-hosted runners`.
  Auto-closes via `closeAlertIssueIfResolved()` once a repo has no more
  violations.

## Owner requirement

For Dependabot's updater specifically, the runner is controlled **org-wide**,
not per repo (#2322 comment): Org Settings → Security → Advanced Security →
Global settings → Dependabot → Runner type → Labeled runner → Runner label.
Both self-hosted runners already answer `self-hosted,linux`, so pointing that
field at `linux` moves every repo's Dependabot updater onto self-hosted
runners with no per-repo change possible or needed — the scanner's alert body
states this exact remedy (menu path) rather than attempting a per-repo fix,
since there is no per-repo API for it. Detection stays valuable even after the
org setting is corrected: it is the only signal that would catch a repo
drifting back onto billed runners later.

## Implementation notes

- Repos are scanned concurrently (`REPO_CONCURRENCY = 4`) via
  `mapSettledWithConcurrency`; one repo's failure doesn't block others'
  (`reportError`, not a thrown exception).
- Does not create worktrees, PRs, or invoke Claude — purely a `gh` API scan
  with issue creation via `ensureAlertIssue()`.
